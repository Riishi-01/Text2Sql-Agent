## FS-001 — R5 allow-list fires on CTE names

**Status:** Open · **Severity:** Blocker (4 cases dead on arrival) · **Cases:** h04, h05, h07, m05

**Symptom:** `SQL validation failed: R5 allow-list: Table 'category_delivery_stats' not in allowed list` (and 3 other CTE names).

**Root cause:** The R5 validator scans the `FROM` clause for any identifier and checks it against the base-table allow-list. It does not distinguish between a base table name (`orders`) and a CTE alias (`category_delivery_stats AS (...)`).

**Fix:** Subtract CTE names from the FROM-clause reference set before the allow-list check.

```diff
- from_refs = {ref.name for ref in tree.find_all(exp.Table)}
+ cte_names = {cte.alias_or_name for cte in tree.find_all(exp.CTE)}
+ from_refs = {ref.name for ref in tree.find_all(exp.Table) if ref.name not in cte_names}
```

**If the validator is locked** (third-party lib), use a prompt workaround: prefer subqueries (`FROM (SELECT ...) AS sub`) over CTEs.

## FS-002 — Rubric marks time_frame wrong for `EXTRACT(field FROM x)` vs `DATE_PART('field', x)` / `TO_CHAR(x, fmt)`

**Status:** Open · **Severity:** High (4 cases fail; both forms are semantically identical in Postgres) · **Cases:** h09, h10, m01, m08

**Symptom:** All 4 cases show `time_frame=wrong` even though predicted SQL computes the same result as gold. Example: gold uses `DATE_PART('day', x - y)`, agent uses `EXTRACT(DAY FROM x - y)` — equivalent in Postgres but flagged.

**Root cause:** The `time_frame` grader does an exact-text keyword search for the gold's operator form. It doesn't know `EXTRACT` is a Postgres alias for `DATE_PART`.

**Fix:** Accept all four forms as equivalent. Check the type of operation, not the function name.

```diff
- if "extract(" in predicted_sql.lower() and "extract(" not in gold_sql.lower():
-     out["time_frame"] = {"status": "wrong", ...}
+ TIME_FNS = ["EXTRACT(", "DATE_PART(", "TO_CHAR(", "STRFTIME(", "DATE_TRUNC("]
+ pred_uses_time_fn = any(fn in predicted_sql.upper() for fn in TIME_FNS)
+ gold_uses_time_fn = any(fn in gold_sql.upper() for fn in TIME_FNS)
+ if gold_uses_time_fn and pred_uses_time_fn:
+     out["time_frame"] = {"status": "correct", ...}
```

## FS-003 — Agent over-filters with `WHERE order_status = 'delivered'` and forgets `+ freight_value`

**Status:** Open · **Severity:** High (3 cases with wrong semantics) · **Cases:** h08, m03, m10

**Symptom:** The agent adds `WHERE order_status = 'delivered'` to queries that don't ask for "delivered orders". It also drops `+ freight_value` from `SUM`, undercounting revenue by ~14%.

**Root cause:** The system prompt doesn't emphasize (a) no scope creep, (b) revenue always includes freight, (c) per-customer metrics need pre-aggregation per order (grain trap).

**Fix:** Prompt-only.

```yaml
NEGATIVE CONSTRAINTS:
- Do NOT add WHERE clauses the question didn't ask for. Only filter on
  order_status when the question explicitly says "delivered" / "shipped" / "canceled".
- For revenue/SUM, ALWAYS include both price and freight_value. Revenue
  without freight undercounts by ~14%. Use SUM(price + freight_value).
- For per-customer / per-state aggregations, PRE-AGGREGATE per order in a
  subquery first. AVG on joined rows averages line items, not orders.
- Return EXACTLY the columns asked for. No "helpful" extras.
```

## FS-004 — Wrong output shape: "how many" questions return rows instead of a count

**Status:** Open · **Severity:** Medium (1 case; affects all "how many" questions) · **Cases:** e06

**Symptom:** "Orders delivered late" returns up to 1000 rows with `order_id, days_late, ...`. Gold returns one row with `count = 7826`.

**Root cause:** The agent doesn't distinguish "show me X" from "count X". The prompt has no output-shape guidance.

**Fix:** Prompt + new example.

```markdown
OUTPUT SHAPE:
- "How many / count of / number of" → return ONE row with COUNT(*).
- "Top N X by Y" → return N rows ordered by Y.
- "Show me X" / "list X" → return all matching rows.
- "Average / sum / total of Y" → return one row with the aggregate.
```

## FS-005 — `customer_id` vs `customer_unique_id` grain mistake

**Status:** Verified · **Cases (historical):** e02, m04, m10, h01, h02

A single person has multiple `customer_id`s (one per order). Use `customer_unique_id` for per-customer metrics. The agent has clearly learned this trap — no new occurrences in the v1 run.

## FS-006 — Agent over-defensively wraps with `COALESCE(category_name_english, category_name)`

**Status:** Open · **Severity:** Low (works correctly, just stylistically noisy) · **Cases:** e01, e03

**Symptom:** Gold uses `WHERE t.product_category_name_english = 'health_beauty'`. Agent uses `WHERE COALESCE(t.product_category_name_english, p.product_category_name) = 'health_beauty'`. Both return the same rows; rubric flags as `filters=wrong` due to text mismatch.

**Root cause:** Rubric's `filters` check does exact-text comparison of WHERE clause strings. It doesn't recognize the `COALESCE(t.col, p.col) = 'X'` form as semantically equivalent to `t.col = 'X'`.

**Fix:** Rubric — verify the semantic intent of each filter (column + value), not the exact text. The COALESCE pattern is actually more robust in production (FS-007).

## FS-007 — Should we keep the COALESCE pattern? (open decision)

**Cases affected:** all category-translation queries (e01, e03, m01, m05, h04, h05, h07, h08)

The COALESCE form handles NULL translations gracefully. Olist happens to have 100% coverage so both forms return the same data, but in any other dataset the gold form would silently miss rows.

**Recommendation:** accept COALESCE as a pass (loosen rubric). The rubric is a grading tool, not a style guide.

## FS-008 — EM is literally 0% across the whole run

**Status:** Open · **Severity:** Medium (weak signal for NL2SQL)

EM rate = 0% across all 39 cases. No predicted SQL is byte-identical to gold after normalization. NL2SQL agents produce semantically equivalent but syntactically different SQL (whitespace, aliasing, COALESCE wrapping, subquery vs CTE, EXTRACT vs DATE_PART). Exact-match is too strict.

**Fix:** Stop reporting EM as a primary metric. EX is the meaningful one.

```diff
- em, em_norm = grade_em(predicted_sql, gold_sql)
- rubric["em"] = em
+ em = 0  # always 0 for NL2SQL; not a useful signal
```
