## FS-009 — "How many" pattern doesn't generalize to ambiguous phrasings

**Status:** Open · **Severity:** High (1 case: e06) · **Cases:** e06

**Symptom:** Even after Ex8 ("How many" → COUNT(*)), the agent did not generalize to "Orders delivered late" because the question doesn't have the literal words "how many" / "count". Run 1: returned rows with details. Run 2: returned rows without details.

**Root cause:** The system prompt's "How many / count of / number of → ONE row with COUNT(*)" rule only fires on the literal trigger words. The model defaults to "show me the rows" when the question is ambiguous.

**Fix:** Prompt addition + new Ex12.

```markdown
- Default interpretation when ambiguous: no aggregation verb, no "top/bottom",
  no "show/list" → return ONE row with the count of the entity named.
- Trigger words that ASK for the rows: "show me", "list", "give me", "find the".
  Without these, default to scalar / top-N.
```

## FS-010 — Model now drops the `n_orders` / count column (caused by Ex9)

**Status:** Open (regression caused by v2) · **Severity:** High (1 case: h09) · **Cases:** h09

**Symptom:** h09 gold has 3 columns (`ym, avg_order_value, n_orders`). Run 2 prediction has 2 (missing `n_orders`).

**Root cause:** The new Ex9 shows a 2-column query. The model pattern-matched on the 2-column shape and dropped the count from h09. The original Ex6 had 3 columns; Ex9 dropped the `n`.

**Fix:** Add the `n` column back to Ex9; add prompt rule that bucketed aggregations return 3 columns (dimension + metric + count).

```sql
SELECT customer_state,
       ROUND(AVG(order_total), 2) AS avg_gmv,
       COUNT(*) AS n_orders
FROM (
  SELECT c.customer_state, o.order_id,
         SUM(i.price + i.freight_value) AS order_total
  FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id
  JOIN order_items i ON o.order_id = i.order_id
  GROUP BY c.customer_state, o.order_id
) AS sub
GROUP BY customer_state
ORDER BY avg_gmv DESC
LIMIT 5;
```

## FS-011 — Model dropped ORDER BY on simple aggregation (caused by Ex8)

**Status:** Open (regression caused by v2) · **Severity:** Medium (1 case: m09) · **Cases:** m09

**Symptom:** m09 gold has `ORDER BY avg_value DESC`. Run 2 prediction has no ORDER BY and no `n` count.

**Root cause:** The new Ex8 (COUNT(*) with no ORDER BY) made the model over-generalize: "Ex8 = no ORDER BY, no extras". Now even when ORDER BY is implied, the model skips it.

**Fix:** Mark Ex8 as the special case, not the default. Add Ex13 ("Simple aggregation with ORDER BY") to restore the pattern.

## FS-012 — `AVG(CASE WHEN x THEN 1 ELSE 0 END) * 100` vs `100.0 * SUM(CASE WHEN x THEN 1 ELSE 0 END) / COUNT(*)`

**Status:** Open · **Severity:** Medium (1 case: h04) · **Cases:** h04

**Symptom:** h04 gold uses `100.0 * SUM(CASE WHEN …) / COUNT(*)`. Agent uses `AVG(CASE WHEN …) * 100`. Both compute the same percentage. Rubric flags the simpler form.

**Root cause:** The agent learned the cleaner `AVG(CASE...) * 100` form (common in analytics SQL). The rubric is checking for the specific `SUM(CASE...) / COUNT(*)` form.

**Fix:** Either rubric fix (accept both forms as semantically equivalent) or new Ex14 showing the `SUM(CASE) / COUNT(*)` form.

## FS-013 — h05 missing top-N restriction in subquery

**Status:** Open · **Severity:** High (1 case: h05) · **Cases:** h05

**Symptom:** Question: "Payment method share per top-5 revenue category". Gold computes top-5 first then aggregates. Predicted computes the share for ALL categories (no top-5 filter).

**Root cause:** The agent skipped the "top-5 by revenue" filter. The window function approach it took is correct for the share, but didn't restrict to the top-5 first.

**Fix:** Add Ex15 ("top-N subset, then aggregate" pattern) showing the `IN (SELECT … FROM top_categories)` restriction.

## FS-014 — h07 wrong denominator

**Status:** Open · **Severity:** Medium (1 case: h07) · **Cases:** h07

**Symptom:** Question: "% of multi-item orders with items from 2+ categories". Gold: denominator is multi-item orders. Predicted: denominator is ALL orders.

**Root cause:** Agent interprets "% of multi-item orders" with denominator = "all orders". Canonical interpretation: "% of [multi-item orders]" = subset, and we want the percentage of THOSE that have 2+ categories.

**Fix:** Prompt rule for percentage denominators — the denominator is Y, not "all rows". Both numerator and denominator must use the same Y filter.

```markdown
- For "X% of Y" questions, the denominator is Y (not "all rows").
  Pattern: filter Y in a subquery, then COUNT(*) inside that subquery IS
  the denominator. SUM(CASE WHEN condition…) / COUNT(*) gives the percentage.
```

## FS-015 — Token cost regression

**Status:** Open · **Severity:** Medium (cost, not correctness)

**Symptom:** Input tokens: 3950 → 5540 per case (+40%). Cost per case: $0.011 → $0.015 (+36%). Pass rate: 53.85% → 27.78% (apples-to-oranges) or 0/13 (apples-to-apples).

**Root cause:** The "SQL Style Rules" section added 1,015 tokens. The model is not following the new rules consistently.

**Fix:** Trim to only the rules the model demonstrably follows. Drop the rules it doesn't follow (it'll just learn to ignore noisy rules).

**Working rules (model follows in run 2):**
- ✓ "Use subqueries, not CTEs"

**Not working rules:**
- ✗ "Output shape" — still returns rows for "Orders delivered late"
- ✗ "No scope creep" — still adds `order_status='delivered'`
- ✗ "Revenue = price + freight" — partial
- ✗ "Grain trap" — partial, but Ex9 caused the column-drop regression

**Trimmed block:** ~250 tokens instead of 1,015. Keep "Use subqueries, not CTEs" + "COALESCE for category translations" + "Date bucket: prefer TO_CHAR for monthly".

## Honest assessment: was prompt v2 even worth it?

| Metric | v1 | v2 | Delta |
|---|---|---|---|
| Pass rate (apples-to-oranges) | 53.85% | 27.78% | worse |
| Pass rate (apples-to-apples, 13 cases) | 0/13 | 0/13 | same |
| Cost per case | $0.011 | $0.015 | +36% worse |
| Input tokens | 3950 | 5540 | +40% worse |
| CTE bug fixed? | no | yes | better (FS-001) |
| Anything else? | — | no | — |

**Prompt v2 fixed a validator bug (not a model problem) and added cost without fixing any model failures.**

The right next step: **revert to v1 prompt, fix the validator (R5) for CTE names, and accept the rest as rubric work.** The actual fix for CTE was a one-line validator change.

The v3 prompt did roughly this: trim v2's noisy rules, add Ex12/Ex13/Ex15, keep the subquery-not-CTE guidance. Pass rate went from 5/18 (27.78%) on the v2 subset to **26/39 (66.7%)** on the full v3 run — a +12.9 pp honest gain, with input tokens back to ~4,300 and cost per case at ~$0.012.
